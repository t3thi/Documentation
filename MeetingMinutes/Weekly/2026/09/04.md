## Topic 2: Semantic Scope of the All-Languages Marker

The group began the planned comparison between Gerrit changes [95619, “Introduce a marker for the ‘all languages’ value”](https://review.typo3.org/c/Packages/TYPO3.CMS/+/95619) and [92267, “Mark LanguageAll record handling”](https://review.typo3.org/c/Packages/TYPO3.CMS/+/92267). The aim was to identify false positives and gaps before forming a shared opinion on the broader patch.

The review exposed two meanings currently represented by the literal value `-1`. For a database record with `sys_language_uid = -1`, it expresses an actual Language-All record that is intended to be available in every frontend language. In other places, the same value is synthesized by backend code to represent a display option such as showing all languages together.

André considered a common marker reasonable because both cases refer to all languages. Eric emphasized that using one marker conceals an important distinction for subsequent work. The initiative's current direction is to eliminate synthetic `-1` values from backend display and selection logic wherever the same state can be expressed explicitly. The value `-1` should then remain associated only with an editor deliberately selecting Language All in a record's language field, which the initiative interprets as synchronization intent. This direction still requires further call-path analysis and was not treated as an already verified Core-wide rule. Benni had explicitly invited contributions to his patch.

The group rejected adding All Languages to the Editing Language selector. Editing requires one concrete primary language, whereas the separate comparison-language selector controls which additional language overlays are visible. Because TYPO3 v15 provides a multi-select that can explicitly select every available overlay, the group questioned whether a synthetic `-1` is still necessary to represent “show all languages” in this backend context. The `Site` and `SiteLanguageAccessorTrait` occurrences were selected for further investigation rather than classified immediately.

> **Core-code validation after the meeting:** The check against Core `main` at commit `028b93bddf49a950eb3a58c4606b5e06145fb567` showed that these two occurrences currently have distinct active responsibilities. `Site::getAvailableLanguages()` can add a synthetic `SiteLanguage(-1, ...)`, which `PageLayoutContext` still uses when representing Language-All records in the Layout module. Separately, the routing `SiteLanguageAccessorTrait` deliberately places `-1` first when resolving language-aware records; its documentation describes it as “all language (-1), most specific if present since there cannot be any localizations.” This confirms current dependencies, but not that the synthetic representation remains necessary. A follow-up analysis must determine which call paths can use explicit language selections instead and which uses represent an actual record-level Language-All value.

## Topic 3: Review of Specific Core Usages

In the Workspaces `ReviewController`, the marker appeared to represent a backend view option rather than a Language-All database record. The group left this occurrence unchanged for the time being because the surrounding review interface required further analysis. The subsequent Core-code check confirmed that `ReviewController::getSystemLanguages()` converts the synthetic language UID `-1` to the string value `all` and passes it to the Workspaces language filter. This makes the occurrence a candidate for the planned removal of synthetic `-1` handling, but does not by itself prove that it can be removed safely.

In `RecordsXmlSitemapDataProvider`, the query includes both the active language and Language-All records. This allows records from a configured language-aware table, such as News entries with `sys_language_uid = -1`, to appear in every relevant sitemap. The group classified this as a valid record-level Language-All use and therefore as an intended finding of the marker patch. The Core-code check confirmed that the provider resolves the table's configured language field and restricts it to exactly `-1` and the current language ID.

These examples reinforced the need to evaluate each occurrence by its behavior and data semantics instead of treating every literal `-1` as interchangeable.

## Topic 4: Recycler Language Selector Consistency

Runtime inspection of the TYPO3 v15 backend showed that the Recycler's language filter differs from the multi-language selectors used by the Layout and Records modules. A deleted Language-All record was displayed with an All Languages label, but the Recycler did not offer a dedicated way to select only that value.

The group agreed that the Recycler should adopt the shared selector behavior used by the other modules and accept an array of selected languages, while retaining its own processing logic where necessary. Selecting every available language should be represented by that explicit array rather than by a synthetic `-1`. A dedicated Language-All filter option was not preferred because the long-term direction is to remove `sys_language_uid = -1`. Instead, records whose language field actually contains `-1` should be visible in the Default Language context consistently with the Records module. A Core issue should be created to track this alignment.

> **Core-code validation after the meeting:** The observed divergence is present in `main`. The Recycler uses radio buttons; its All entry maps to `null` and therefore disables language filtering, while a concrete selection is matched by exact language ID. In contrast, the Layout and Records modules use the shared `LanguageSelectorBuilder`, and the Records query adds `-1` to the selected language IDs. Accepting multiple IDs and including Language-All records in the Default Language context are therefore proposed changes, not current Recycler behavior.

## Topic 5: LinkValidator Language Semantics and Runtime Verification

The `LinkAnalyzer` associates a broken-link entry with the language of its containing record. For a language-aware table with a populated language field, this is the stored language value, including `-1` for a Language-All record. If the table is not language-aware, or if the resolved field is absent or unset in the row, the analyzer stores `-1` as a fallback. This is another case where one value currently covers technically different semantics. Under the initiative's current direction, the fallback should eventually be represented without reusing the record-level Language-All value, subject to further code analysis.

During runtime verification, an initial TYPO3 v15 test did not produce the expected broken-link entries. Martin then reproduced an internal broken link in TYPO3 14.3.6 and changed the containing record to Language All. The LinkValidator listed the broken link and displayed its localization as All Languages, confirming that the record-level value is represented in the result. The subsequent Core-code check confirmed the full rendering path: the controller resolves the stored `-1` through the system-language list, and the report template renders the resulting All Languages title and multiple-flags icon.

André shared the [LinkValidator configuration documentation](https://docs.typo3.org/c/typo3/cms-linkvalidator/main/en-us/Configuration/Index.html#confval-tsconfig-linktypes) and the [TYPO3 v13 breaking change that disabled external link types by default](https://docs.typo3.org/c/typo3/cms-core/main/en-us/Changelog/13.0/Breaking-101671-DisableExternalLinktypesByDefaultInEXTlinkvalidator.html). External-link validation must now be enabled explicitly, which explained why an external test link was not checked under the default configuration.

The group left the representation of the mixed `LinkAnalyzer` semantics open and planned to continue the patch review at the next meeting.
