## Topic 1: Strict Fallback Type and the Scope of the Patch

Eric introduced [patch #94510, “Restrict language fallback chain”](https://review.typo3.org/c/Packages/TYPO3.CMS/+/94510), after Georg had requested his input. The patch stops a hidden translated record from falling back to another language under `fallbackType: strict`. A missing translation can still trigger fallback to a configured fallback language. Eric questioned the latter behavior, made explicit by the test `missingTranslationInStrictModeFallsBackToConfiguredFallbackLanguage()`.

The participants referred to [Feature #88137, “Multi-level fallback for content in frontend rendering”](https://docs.typo3.org/c/typo3/cms-core/main/en-us/Changelog/12.2/Feature-88137-Multi-levelFallbackForContentInFrontendRendering.html). Their understanding was that `fallbackType: strict` should render content explicitly translated or created in the selected language, preserve the sorting of default-language content elements and include floating content elements through `LanguageAspect::OVERLAYS_ON_WITH_FLOATING`, but not apply a content fallback chain. They distinguished `fallbackType: free`, which does not apply record overlays to content elements.

Eric initially associated the disputed behavior with [patch #83169, “Respect language fallback chain for record overlay”](https://review.typo3.org/c/Packages/TYPO3.CMS/+/83169). During preparation of the review comment, they deliberately left out the causal attribution rather than present it as established without further checking. They wanted the Core Team to clarify the intended fallback behavior, not merely infer it from an existing implementation or test.

## Topic 2: Regional Fallback Without the Default Language

The discussion revisited Johannes's use case in [Forge ticket #110008](https://forge.typo3.org/issues/110008): German is the default language, British English should fall back to general English, but not to German. Eric explained that this requirement had led to using `fallbackType: strict` with a configured fallback chain because `fallbackType: fallback` ultimately renders default-language content when no translation is available in the chain.

Eric preferred using only the configured fallback languages under `fallbackType: fallback`: if language `0` is not explicitly selected, TYPO3 should not implicitly fall back to the default language. He checked that the backend permits selecting `0` explicitly as a fallback language. In that proposed behavior, `fallbackType: strict` would not evaluate a content fallback chain, while `fallbackType: fallback` would support the required regional fallback without rendering German content.

The participants distinguished the final fallback language from the separate requirement to hide an individual content element in one language despite a configured fallback chain. They did not select a complete implementation or migration strategy for either problem.

## Topic 3: Intentional Absence and Translation-in-Progress Workflows

Eric considered a hidden translation a possible way to express that a structurally present content element should deliberately not be rendered in one language. Martin pointed out a conflicting workflow: an editor may create a hidden translation, work on it, and unhide it only when ready. If creating that hidden translation immediately stops fallback, content previously rendered in the frontend disappears throughout the translation process.

They treated both intentional absence and unfinished translations as valid needs. Using the same `hidden` field for both does not distinguish the editor's intent. They considered a separate translation-in-progress state, Workspaces and an additional field for hiding content in a specific language, but did not choose a new field or state model. Workspaces were recognized as relevant to unpublished changes, not established as the complete answer to this discussion.

Eric retained intentional absence as an important requirement within “mostly connected, selectively different” content. Martin stressed that these additional editorial features should be handled separately from the patch. The discussion did not establish that every hidden translation means intentional absence or that existing editorial workflows may safely be changed without further consideration.

## Topic 4: Compatibility, Live Verification, and the Gerrit Review

André and Martin favored keeping broader behavior changes on `main` or in follow-up patches. Eric emphasized the unresolved needs of existing TYPO3 v14 installations and considered accepting the bugfix there while clarifying the intended fallback behavior on `main`. They did not reach a final release or backport decision.

A live comparison during the meeting showed that the patch prevented fallback for a hidden British-English translation under `fallbackType: strict`. Switching the site language to `fallbackType: fallback` continued to render fallback content. The participants distinguished this functional result from agreement with the intended behavior: the patch worked for its stated case, but did not provide intentional absence under `fallbackType: fallback` or settle whether `fallbackType: strict` should evaluate a content fallback chain at all.

They formulated a review referring to Feature #88137, questioning the test's assumption and asking Benni for clarification. André posted the comment with `Verified +1` and `Code-Review -1`. The positive `Verified` vote therefore did not mean that the patch had been approved for merge. The group left the intended fallback behavior open for Core discussion.

## Topic 5: Crop Changes Not Propagated to Translated File References

André reported a record with an image field configured as `l10n_mode=exclude`. Creating the translation initially copied the file reference, including its crop configuration, but subsequent changes to the `crop` field in the default language were not synchronized to the translated `sys_file_reference` record. Because the image field was synchronized and could not be edited independently in the translation, the expected result was that the crop configuration should also be synchronized.

The discussion revisited [Forge ticket #88024, “allowLanguageSynchronization doesn't synchronise cropping from images”](https://forge.typo3.org/issues/88024). It covers the same distinction between synchronizing a file relation and synchronizing subsequent changes to the related file reference record, including `allowLanguageSynchronization` and `l10n_mode=exclude` configurations.

They reviewed an older workaround enabling `allowLanguageSynchronization` on `sys_file_reference.crop`. The historical result distinguished an image field set to “Value of default language” from one set to “Custom value”. André reported that a colleague's recent attempt had not worked and wanted to check the behavior in TYPO3 v13 against the older experience. The meeting did not verify a current workaround or identify the cause of a new regression.

## Topic 6: IRRE Child Records Versus Shared MM Records

Eric preferred deriving synchronization from the parent file field instead of configuring all `sys_file_reference` records globally. His expectation was that synchronizing the file field should also synchronize its related file reference records, including their crop configuration, while other file fields could still use language-specific values. They noted that current `TCA` uses the dedicated field type `file` rather than `ExtensionManagementUtility::getFileFieldTCAConfig()` and wanted to inspect how `DataHandler` processes the underlying file relations.

They extended the requirement to parent-owned one-to-many IRRE relations, such as card records belonging to a content element. In this model, each child record belongs to one parent and is an integral part of that parent, rather than an independently shared record. Synchronizing the parent's relation field should therefore also synchronize the relevant fields of its child records, including nested parent-owned IRRE child records.

This is distinct from an MM relation, where multiple parent records can reference the same independently managed record. Synchronizing one parent's relation field should not automatically overwrite the shared target record and thereby affect its other usages. This distinction addresses André's concern about records being referenced elsewhere: the proposed recursive synchronization concerns parent-owned children, not arbitrary records reachable through relations. It remains proposed behavior, not a verified guarantee for every `inline` configuration.

> **Post-meeting Core code verification:** The TCA type `inline` alone does not establish this ownership model; the relation configuration, including `MM`, must be considered. For a `file` field, the parent-owned child is the `sys_file_reference` record, not the referenced `sys_file` record, which can be shared. Synchronizing the relation does not automatically enable language synchronization for every child field: the standard `sys_file_reference.crop` field has neither `l10n_mode=exclude` nor `allowLanguageSynchronization`. Cascading deletion also depends on the relation configuration, including `behaviour.enableCascadingDelete`.
