## Topic 2: Purpose and Scope of the Language-All Marker

Eric summarized the background of [Gerrit change 95619](https://review.typo3.org/c/Packages/TYPO3.CMS/+/95619), for which he had prepared further changes but had not yet uploaded a new patch set. The change introduces a named marker for occurrences where `-1` semantically means All Languages. This includes both values stored in a record's language field and synthetic values used by backend selectors, filters or other Core logic.

Eric related this work to the initiative's broader goal of separating language identity from additional behavior. Neither `sys_language_uid = -1` nor `sys_language_uid = 0` represents only a concrete human language: `-1` also introduces language-wide behavior, while `0` combines the Default Language with a structural role. Separating those responsibilities would allow a semantic language identifier such as `BCP 47` to describe the actual language independently. The current direction for replacing stored Language-All records remained an explicit synchronization intent, potentially represented by a Boolean flag on a source record, rather than preserving `-1` as a language identity.

The team retained its earlier decision to use one marker within the bounded patch wherever `-1` means All Languages. The marker is therefore not limited to values read from database records. Unrelated uses of negative one, such as arithmetic or positional calculations, remain outside its scope.

## Topic 3: TCA and SlugHelper Coverage

The team reviewed several occurrences that had not been covered consistently by the earlier patch description. The description had explicitly excluded TCA handling, but the inspected code used `-1` with a direct All-Languages meaning. In `TcaColumnsRemoveEmptyRelations`, the value participates in determining whether a field offers multiple language choices. `TcaEnrichment` and `TcaPreparation` add `foreign_table_where` restrictions that include All Languages together with the Default Language. The participants agreed that these were genuine marker usages and that excluding them would conflict with the patch's purpose.

The team therefore chose to include clear TCA occurrences and update the commit message accordingly. Eric also showed an occurrence in `SlugHelper` where nearby code already used the marker but a further literal `-1` remained. Because the code explicitly handled All Languages, the team regarded this as an overlooked replacement rather than a separate semantic case.

## Topic 4: LinkValidator Fallback Semantics

The participants revisited the `LinkAnalyzer` behavior discussed in earlier meetings. When the analyzed record is language-aware and its language field is available, the generated broken-link entry retains that value. Otherwise, the entry falls back to the All-Languages marker. This means that records without language support are represented as applicable to all languages. Eric also considered whether a language-aware record might reach this point without its language field having been selected, which would incorrectly trigger the same fallback. After tracing the generic table and field processing, the group regarded that risk as low but did not claim that every possible call path had been proven.

André considered the fallback appropriate because a link from a non-language-aware record may be relevant across languages. The team accepted the existing occurrence for the marker patch and retained the current behavior. It also reviewed `EditableRestriction`, which includes All Languages when it limits broken-link entries to languages available to the backend user. Because that restriction consumes the same LinkValidator representation, the team considered use of the named marker consistent there as well. The cast to string was left unchanged because altering the query representation was outside the patch's scope.

## Topic 5: Marker Documentation and PHP Compatibility

The team reviewed revised documentation for the `LanguageMarker` class and its `ALL_LANGUAGES` constant. André identified that the proposed opening fragment lacked a verb, and the participants reformulated it to describe the introduction of reserved language values that do not point to a configured site language. They retained the description of the class as a set of markers rather than an enum: ordinary language values remain integer IDs of site languages, while the constants name values with special semantics.

For `ALL_LANGUAGES`, the revised documentation states that a record carrying the value in its language field is valid in every language of a site, is neither translated nor overlaid, and that backend logic, selectors and filters may use the same value even when it was not read from a record. It also distinguishes unrelated uses of `-1`, such as calculations. The team removed a redundant short line that repeated the constant name without adding meaning and accepted the resulting class and constant descriptions.

The group also discussed the typed declaration `public const int ALL_LANGUAGES = -1`. TYPO3 v15 currently requires PHP 8.5, so the type is valid on `main` and should remain there. A possible TYPO3 v14 backport would have to remove the type for PHP 8.2 compatibility. André expected the backport's automated checks to expose that incompatibility and advised against adding an explanatory patch comment solely for this purpose.

## Topic 6: TypeScript Drag-and-Drop Boundary

The review found a Language-All literal in the Layout module's TypeScript drag-and-drop handling. The code preserves the language when the dragged content element uses `-1`; otherwise, it adopts the target column's language. The PHP marker cannot be referenced directly from TypeScript without introducing a cross-language representation.

For the current patch, the participants preferred to retain the literal and add a comment that it must stay synchronized with `LanguageMarker::ALL_LANGUAGES` on the PHP side. André considered a shared TypeScript constant preferable to repeatedly passing a value through generated markup if more JavaScript occurrences emerge. Eric also presented a possible follow-up in which the drag-and-drop data would expose an explicit `isAllLanguage` property. The group regarded either implementation as a behavioral and architectural follow-up rather than part of the current marker-only patch.

## Topic 7: Remaining Findings and the Next Patch Set

Eric presented seventeen further findings for which the analysis had prepared proposed dispositions: twelve context-only cases, one retained literal and four possible follow-up patches. One context-only example restricted a page translation parent selector to the Default Language without containing `-1`. The team discussed whether code that explicitly excludes or never permits All Languages should also receive an annotation. Such context may become relevant when Default Language handling is examined, but it does not itself provide a literal that the current patch can replace.

The discussion also touched on range checks such as `currentLanguage > -1`, which implicitly exclude All Languages without directly comparing equality with the marker. The participants did not settle a general rule for annotating all such inverse or context-only cases and agreed to continue that discussion in the next meeting.

Eric planned to upload the expanded patch set first and add a review comment if it received no response. He would also revise the commit message to remove the record-field-only framing, explain that the marker covers synthetic All-Languages contexts, and no longer exclude the accepted TCA occurrences. The team accepted that the wording could be refined again during review.
