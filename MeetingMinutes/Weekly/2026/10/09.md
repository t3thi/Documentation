- **Participants:**

## Topic 1: Merged Language-All Marker and Default Language Follow-Up

Eric reported that [Gerrit change 95619, “Introduce a marker for the all languages value”](https://review.typo3.org/c/Packages/TYPO3.CMS/+/95619) had been merged. The participants regarded the named marker as a first preparatory step towards replacing the special handling of `-1`.

André proposed identifying the Default Language value `0` through a marker as well. He expected the initiative to encounter `0` checks while changing Language-All handling, because the two values interact in existing code. Eric agreed that identifying these occurrences was a useful next step for understanding the affected scope.

## Topic 2: Migration Abstractions and Query Boundaries

Eric asked whether TYPO3 v15 could provide an abstraction that extension developers could adopt before the underlying Language-All representation changes. A named constant still leaves the code dependent on an integer in a record's language field, including comparisons and numeric boundary checks. It does not by itself make a Boolean synchronization flag or a different representation interchangeable with `sys_language_uid = -1`.

The participants considered a record-level helper such as `isLanguageAllRecord` and a corresponding Default Language check. While inspecting `DataHandler`, they distinguished the language of the existing row from a language supplied through a copy or move update. Because the rows are arrays rather than objects, a utility accepting a record was one possible form. It would also have to resolve the table's language field, which is defined through `TCA` rather than universally fixed to one field name.

André emphasized that a per-record predicate would not solve query-level selection. A query must collect records for the requested language and express whether Language-All records are included or excluded. Eric considered integrating that responsibility through query restrictions, initially preserving the existing comparison against `-1`. The participants also recognized that the required behavior depends on the calling context and cannot simply be made one global restriction.

Eric questioned whether wrapping every database-level check would add complexity without sufficient benefit. The alternative would be to change the affected code directly when the representation changes. The discussion did not select a migration API or utility design.

## Topic 3: Concrete Language Variants and Copy or Move Semantics

André pointed out that the intended synchronization model could eliminate many Language-All checks entirely: if a concrete record exists in each target language, a query can select that language's records without additionally including a shared `-1` record. Eric agreed that this might make an intermediate abstraction unnecessary in some code paths.

The participants explored the consequences for copy and move operations. Eric argued that a record already synchronized into other languages could not simply be moved into a language where its corresponding variant already exists. Other records without such variants could still have different move behavior. Copying content marked for all-language synchronization would need to insert the corresponding content across the affected languages, rather than derive its meaning solely from the language in which the editor invokes paste.

Eric initially considered offering paste only in the Default Language or structural reference layer, then noted that this would conflict with hiding that layer from editors. Paste controls might instead remain available in every working language while invoking the same synchronization operation.

## Topic 4: Structural Reference and Editing Shared Content

The team related the `0` and `-1` work to its broader aim of identifying actual languages through `BCP 47`. André described his still-unimplemented prototype concept in which `0` would remain only as an invisible structural reference rather than a content language. He questioned whether Language-All behavior could then be represented within the same non-language structure, possibly with an additional flag, instead of maintaining two separate special language values. The discussion did not settle that representation.

Eric raised the editorial consequence of removing the visible Default Language layer: content currently maintained there as Language All would still need to be editable. André distinguished the interface from storage and suggested showing shared content in every language while retaining its underlying representation. Eric explored a more explicit alternative with synchronized concrete variants, where an edit in any language propagates to the others, potentially through the `0` parent and its translation relations. Such preparation could simplify `-1` handling and make the structural layer invisible without removing editorial capabilities.

## Topic 5: Current Output Modes and Default Language Visibility

The participants revisited the distinction between the output modes `strict` and `free`. André described the current dependency in `strict`: disabling the Default Language source can suppress its translations in frontend output even though those translations remain enabled in the backend. Eric initially questioned that dependency, then distinguished requesting only the selected language from bypassing the Default Language source altogether.

In the explanation developed during the discussion, `strict` still starts from the Default Language structure and overlays only the requested language, whereas `free` selects that language's content independently of the Default Language source's visibility. They separated this output behavior from the backend's structural relationships and editorial synchronization. The requirement that `strict` must not silently fall back to another language remained distinct from the question of source visibility.

## Topic 6: Intentional Absence Versus Fallback

Eric used a British-English to US-English fallback example to distinguish missing content from deliberately absent content. A missing translation may legitimately use a configured fallback, while an existing translation that an editor explicitly disables can express a wish to show nothing at that position. Returning fallback content in the latter case would ignore that intent.

Eric and André considered a rule in which an existing disabled translation blocks fallback, while a missing translation permits it. Under that proposed rule, deleting the translation would allow fallback content to appear again. They regarded this distinction as compatible with the existing record model, without requiring an additional workaround solely to represent intentional absence.

They also recalled the previously discussed regression in which `strict` considered fallback content. Eric maintained that requesting `strict` must keep output in the selected language. The proposed handling of disabled translations and the correction of an unintended fallback under `strict` were related but separate concerns.

## Topic 7: Simplifying Output Policy Through Explicit Visibility Updates

André proposed replacing the current frontend dependency on Default Language visibility with explicit updates when content is edited. The interface could offer an operation for enabling or disabling only the current language and another for enabling or disabling all related language variants. The all-language operation would set the existing `hidden` value on each affected record, rather than require frontend rendering to repeatedly consult the Default Language parent. APIs would need equivalent support, potentially through an option in `DataHandler`.

In this proposal, output without a fallback chain would select concrete content from the requested language in a Free-like manner. Synchronizing visibility at write time would preserve the relevant existing Strict behavior without a separate frontend `strict` mode. A configured fallback chain would still be evaluated at runtime and would remain part of site configuration. André suggested that the presence or absence of that chain could replace the separate `fallbackType` selector, avoiding a configuration that specifies both `strict` and a fallback chain.

The participants distinguished a structural connection from an instruction to use fallback. Within André's proposed model, a configured chain would permit fallback for connected content, while an explicitly disabled translation would block it locally. Eric also raised the editorial need for broadly connected structures with selected language-specific deviations, including independent sorting. He emphasized that output policy and the way content is maintained or synchronized are different responsibilities.

Eric considered whether fallback could also be materialized through synchronized copies. André noted that synchronizing one visibility field was much simpler than duplicating complete records with inline children and references, which raises the same wider synchronization problem as replacing Language All. His proposal therefore retained runtime fallback-chain handling rather than requiring copies for every fallback result.

Eric and Martin did not yet consider the proposed removal of the mode distinction fully understood. The team planned to revisit the explanation in the following meeting and assess whether it could inform preparatory work for TYPO3 v15.
