## Topic 1: Empty Translation Source Core Fix

Eric reported on Stefan's [Forge issue #110281](https://forge.typo3.org/issues/110281) and the corresponding Core fixes for [`main`, patch #94914](https://review.typo3.org/c/Packages/TYPO3.CMS/+/94914), [TYPO3 14.3, patch #94916](https://review.typo3.org/c/Packages/TYPO3.CMS/+/94916), and [TYPO3 13.4, patch #94915](https://review.typo3.org/c/Packages/TYPO3.CMS/+/94915). The affected translation lookup prefers `l10n_source` whenever a table defines a translation source field. A valid translation with a correct `l10n_parent` but an empty `l10n_source` is therefore not found.

Because `DataHandler::localize()` uses this lookup to detect an existing translation, the missing result permits another translation for the same parent and target language to be created. André had encountered similar states in a customer installation and had previously treated them as migration artifacts. In a large installation using a DeepL integration, repeated translation operations had produced large numbers of unnecessary references and memory-limit failures. The team considered Stefan's fix potentially relevant to that production problem, although André still needed to verify whether both cases had the same cause.

The patch keeps `l10n_source` as the preferred relation and matches `l10n_parent` when `l10n_source` is empty. Eric distinguished this `DataHandler` and repository issue from the initiative's separate backend selector finding.

## Topic 2: Translation Parent Selector Filtering

Eric reported that the two findings from the previous meeting had been documented as [Forge issue #110328](https://forge.typo3.org/issues/110328) for duplicate translation-parent assignments and [Forge issue #110330](https://forge.typo3.org/issues/110330) for the translation wizard's Free Mode source behavior. The team then refined the expected solution for the translation-parent selector.

The selector must primarily exclude parent records that already have an active translation in the current target language, while retaining the parent currently assigned to the edited record. The rule should apply to every translatable table through its TCA `transOrigPointerField`, not only to `tt_content.l10n_parent`.

The team added a narrower compatibility rule for record types. If a table defines a TCA `type` field and that field uses `l10n_mode = exclude`, a potential parent should only be offered when its type value matches the current record. Otherwise, assigning the parent and saving can replace the record type and unexpectedly change the complete editing form. The team deliberately did not extend this equality requirement to every field using `l10n_mode = exclude`. Differences in `colPos`, for example, can be intentional, while many synchronized fields on `pages` or `sys_file_metadata` are not structural prerequisites for choosing a translation parent. Fields using `allowLanguageSynchronization` were left outside the initial scope because their synchronization remains under editorial control.

Eric traced the generated selector to `TcaEnrichment`, which enriches the configured `transOrigPointerField` as a single-select field. The team favored replacing the current generic `foreign_table` selection with a typed `itemsProcessors` implementation that retrieves eligible records directly. Its result should be limited to records from the same table and page in the default language or `sys_language_uid = -1`, exclude parents already occupied in the target language, and apply the type-field condition when required. Eric prototyped the approach during the meeting, and André planned to turn it into a test-backed patch.

## Topic 3: Strict Mode and Non-Default Fallback Chains

The team revisited Johannes' explanation for combining `fallbackType: strict` with a fallback chain. His site uses German as the default language, a general English language, and a UK language. Approximately 95 percent of the UK content should reuse the general English content, while editors localize individual differences such as contact details or suppress selected elements for the UK variant.

This use case exposed the actual limitation. With `fallbackType: fallback`, TYPO3 eventually falls back to the default language, which would introduce German content after the UK-to-English chain. The strict configuration was therefore being used to prevent the unwanted terminal fallback to German while still attempting to use English as an intermediate fallback.

The team regarded the regional fallback requirement as valid but concluded that it should not redefine strict semantics. Strict mode should continue to render only records from the requested language. As a possible Core direction, the team considered making the default language an optional terminal step of `fallback` mode. This would allow an explicit UK-to-English chain without forcing a final fallback to German. A record-level language visibility extension was considered more granular than the underlying site-language requirement.

## Topic 4: Site-Scoped Fallback Language Options

While reviewing the site-language editor, the team found that the fallback-language item processor collects languages from every configured site. It can consequently offer a language as a fallback even when that language is not configured for the current site. Different titles associated with the same numeric language ID are combined into labels such as English with German in parentheses, which initially appeared inexplicable in the interface.

The team reasoned that a fallback language not configured for the current site is normally ineffective because content in that language cannot participate in the site's page-scoped output. Cross-site record usage was considered, but it did not provide an immediate reason for offering unrelated site languages in this selector. Eric wanted to verify the assumption against the complete runtime fallback evaluation, including its page and column constraints, before changing the behavior.

If that verification confirms the analysis, the fallback selector should use only languages configured for the current site. This would remove ineffective choices and make the special aggregation of cross-site language titles unnecessary. The team treated this as a new issue candidate.

## Topic 5: Cross-Site Language Identity and Labels

The site-configuration tests exposed two inverse identity problems. Selecting the same language preset independently in two sites can create the same conceptual language with different numeric IDs. The existing "Use Existing Language" option allows an administrator to reuse an earlier ID, but the team decided not to change preset creation yet because TYPO3 currently lacks a semantic identifier that can prove that two otherwise identical configurations must represent the same language.

Conversely, YAML configuration can associate the same numeric ID with different language titles across sites. In selectors that aggregate these configurations, TYPO3 currently treats the first site's title as primary and appends later titles in parentheses. The team considered this ordering misleading because none of the sites is inherently primary. If such ambiguity remains supported, each title should instead be shown together with its site identifier on equal terms.

Eric and Martin noted that improving these labels would only mitigate a symptom. The strategic solution remains a stable, descriptive language identity shared across sites, which would eliminate both duplicate identities and ambiguous labels.
