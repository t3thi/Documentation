## Topic 1: Merged Mount Point Translation Patch

Eric opened by noting that there had been new activity in the initiative's Slack channel and that André had contributed a Core patch. André confirmed that his [patch #94831](https://review.typo3.org/c/Packages/TYPO3.CMS/+/94831) had already been merged. The patch fixes translated Mount Point handling when the Mount Point page is configured to display itself rather than the mounted page.

André explained the underlying problem. In the affected case, TYPO3 checked the root line with the translated page `pid`, while the root line was resolved through the default-language page. The translated `pid` therefore did not match the root line, the mounted page could not be found, and TYPO3 returned a `404`.

The fix resolves the default-language `uid` through `l10n_parent` before performing the comparison. André emphasized that the functional code change was small and mainly followed Astrid's earlier analysis, while most of the patch consisted of test setup. Eric summarized the outcome as language-aware Mount Points and noted that earlier initiative work had finally reached Core through a practical project need.

André described the real project use case behind the patch. A project uses three sites with different language configurations and a shared global storage area for news-like content. The global storage can hold many translations even when an individual site exposes only a subset of those languages. Mount Points became useful because the editors needed page-based content maintenance while sharing content across sites.

## Topic 3: Free Mode Columns and Default Language Binding

Eric introduced Dennis' new [patch #94917](https://review.typo3.org/c/Packages/TYPO3.CMS/+/94917), which addresses the backend rendering of Free Mode content in language columns. The discussion was connected to the older [patch #92585](https://review.typo3.org/c/Packages/TYPO3.CMS/+/92585), which focused on showing Free Mode content when the default-language column is empty.

Eric explained the TYPO3 v14 context. Since [Forge issue #106649](https://forge.typo3.org/issues/106649), the Content > Layout module always uses `Default-Language-Binding` in language comparison mode and no longer evaluates the previous Page TSconfig setting `mod.web_layout.defLangBinding`. This is useful for Connected Mode because each default-language element defines a row and the corresponding translations appear next to it.

The problem appears in Free Mode. Free Mode elements do not have a default-language parent, but the current layout can still place many Free Mode elements into the visual area of the first default-language row. Dennis had reported that this can make the backend almost unusable in real customer projects when many Free Mode elements exist.

The team compared the behavior with and without Dennis' patch. In a pure Free Mode view, the patch produced the desired separation from the default-language structure. However, when a connected language column was shown at the same time, the patch broke the useful connected grid. Eric concluded that the patch solves the pure Free Mode case, but must go further before it can be merged because mixed language comparison views need to preserve Connected Mode alignment where it still applies.

## Topic 4: Mixed Mode Layout Semantics

The team then focused on Mixed Mode, where some elements remain connected and others have no `l10n_parent`. André found the case hard to reason about because connected elements and independent elements exist side by side, and the question becomes where unconnected elements should appear in relation to the default-language rows.

Eric observed that the current backend display without Dennis' patch treats Mixed Mode similarly to Free Mode once a connection is broken. Elements are grouped under the first default-language cell, and the visual connection between translated elements and their default-language parents is lost. When the connection is restored, the correct row relation becomes visible again.

André suggested that unconnected Free Mode elements should create their own rows. In a pure Free Mode column, records could simply fill rows one after another without dependency on the default language. In a Mixed Mode column, connected elements should stay in their corresponding default-language rows, while additional unconnected elements need their own representation. Eric noted that this likely requires a deeper change to the underlying HTML table layout of the language comparison view.

The team considered the editorial risk of showing Free Mode records in rows next to default-language records, because editors may infer a relation where none exists. The current Free Mode badge may not be enough to communicate that difference clearly. At the same time, André did not consider differing row heights a blocking issue because even connected translations can have different backend preview heights.

## Topic 5: Preventing Duplicate Translation Parents

During the backend review, the team accidentally created a state where two translations pointed to the same default-language parent. Eric treated this as a separate consistency issue. The Page Module should not make it easy to create duplicate `l10n_parent` assignments for one language.

Eric suggested that the `l10n_parent` selection in the record editing form should only offer default-language records that are still available for the current target language. Records that already have a translation in that language should be excluded from the selector. André agreed that this would make the form clearer because editors would only see valid target records when reconnecting an element.

The team discussed deletion and restoration as related edge cases. André pointed out that deleted records may later be restored, and Eric noted that restored records can carry field values that no longer fit the current structure. Workspaces add another layer of complexity. The team therefore kept the immediate idea narrow: the regular Page Module workflow should prevent accidental duplicate parent assignments in the active editing context.

## Topic 6: Translation Wizard Behavior for Free Mode Source Languages

The team then investigated how the new translation wizard behaves when a non-default source language is selected. Eric explained that choosing a source language can affect both `l10n_parent` and `l10n_source`. A translation can take content from a non-default source language while still using the default-language record as its parent when the source is connected.

The behavior differs when the selected source language is in Free Mode. In the tested case, choosing French as a Free Mode source and selecting "Translate" still produced Free Mode records with empty `l10n_parent`, because TYPO3 cannot invent missing connections. Eric and André concluded that the final choice between "Translate" and "Copy" is misleading in this scenario.

André clarified the rule. If the selected non-default source language is connected, both "Translate" and "Copy" still make sense because the editor can either preserve the connection or intentionally create Free Mode records. If the selected source language is already in Free Mode, only "Copy" is structurally possible because no parent connection exists to preserve.

The team formulated this as a future issue: when a non-default source language is in Free Mode, the new translation wizard should not offer a localization-mode choice. It should use the copy behavior directly and avoid suggesting that connected translations can be created from an unconnected source. This would reduce editor confusion because selecting "Translate" currently still results in Free Mode records.

André raised the question of whether hiding the choice could affect DeepL translation integrations such as `EXT:wv_deepltranslate`. Eric considered the DeepL step structurally separate because DeepL translates field content, while the Core workflow decides whether the resulting records are connected or free. André noted that in TYPO3 v14 the DeepL button appears after the copy-or-translate decision, which makes it less likely that simplifying the Free Mode source case would break that integration.
