## Topic 1: Dialog Days Timing and Product Strategy Window

Eric opened the last meeting before the TYPO3 Dialog Days by explaining that he had just booked his travel and accommodation. He referred to a preparatory email from Jana Höfner from the TYPO3 Association board, which framed the event as open dialogue rather than an official decision-making body. Eric considered this relevant because the initiative needs to understand whether translation handling can still be placed visibly in the upcoming TYPO3 product strategy process.

The team discussed the expected timing of the TYPO3 v15 cycle. André recalled that a `15.0` release would likely precede the final LTS release by roughly half a year, based on previous TYPO3 release cycles. Eric connected this with earlier observations that a product strategy usually has to be communicated months before the first major development release, so a strategy decision only in Q4 2026 could be late for concrete TYPO3 v15 direction.

Eric concluded that the Dialog Days are important because they may be one of the few opportunities to place translation handling before the next strategy is finalized. He expected limited speaking time because many topics and participants will be present, so the initiative's message needs to be compact and product-oriented.

## Topic 2: Product Value First for Translation Handling

Eric presented a draft narrative for the Dialog Days. The presentation should not try to sell a finished technical solution. Instead, it should anchor three strategic points: TYPO3 already has a strong foundation for multilingual websites, international projects increasingly need controlled regional content and structure variants, and translation handling should therefore become an explicit strategic product field.

André suggested that the initiative's most important request should be inclusion in the TYPO3 product strategy. A later discovery or prototyping phase can follow from that recognition. Eric agreed that the immediate request is not approval for a large Core implementation, but strategic recognition of the topic and a path toward people who can review, decide, and merge related Core work.

The team agreed to present the topic with product value before technical implications. Current state, practical problems, and user benefits should come before implementation effort. Technical details such as `sys_language_uid = -1` should appear as concrete examples of why the current model creates complexity, but not as the opening argument.

Eric framed the selling point as making work with translations and regional structural deviations more intuitive while reducing technical complexity. This would make TYPO3 more flexible, more robust, less error-prone, and less dependent on project-specific workarounds.

## Topic 3: Localization, Internationalization, and Structure Variants

The team refined the distinction between localization and internationalization. Localization means translating content within a shared structure. Internationalization, in the discussed product sense, means adapting content and structure to specific markets, regions, or language variants.

Eric read a draft structure with five forms of multilingual structure:

- Identical structure, where only field values differ.
- Reduced structure, where individual local content pieces are omitted.
- Enriched structure, where local content is added.
- Changed structure, where content is replaced or reordered.
- Independent structure, where a target market needs its own structure.

The team saw this as a useful way to explain where TYPO3 is already strong and where gaps remain. Identical structures are the classic localization case and work well. Reduced structures are often manageable. Enriched structures are currently difficult because a local addition can force Mixed Mode or a loss of connected behavior, even when most surrounding content should remain connected.

Eric described the strategic gap as "mostly connected, selectively different". The common real-world case is not a fully independent market site, but a shared structure with targeted regional deviations. The initiative wants TYPO3 to handle that middle ground more naturally.

## Topic 4: Core Complexity and Language Identifier Cleanup

André suggested mentioning `sys_language_uid = -1` as a concrete technical example, but only briefly. Eric connected this with Lolli's recurring point that the largest problem is not the complexity of the data itself, but the complexity of the output logic required to handle current cases. Special values such as `sys_language_uid = -1` and `sys_language_uid = 0` contribute to that complexity because they prevent languages from being identified cleanly and consistently.

The team discussed why removing those special values matters. More explicit language identifiers would make languages identifiable across pages, sites, and installations. Eric used translated file metadata as an example where cross-site language identity becomes useful. André clarified that this makes languages more exchangeable and reusable across contexts.

Eric summarized why translation handling is a Core topic. Language relations affect `DataHandler`, `Workspaces`, page and content editing, routing, queries, fallback behavior, permissions, and frontend rendering. André added that `Extbase` rendering and direct Core rendering can behave differently, which reinforces the need to bring those worlds closer together.

The hidden structural layer was described as a hypothesis rather than a finished proposed solution. The underlying question remains how TYPO3 can support structural deviations across language layers while keeping editorial behavior predictable.

## Topic 5: Multi-Dimensional Content Contexts

Eric brought up earlier thoughts around a generic dimension model and Olivier's related ideas. TYPO3 currently has a configurable language dimension, but not a general dimension model. This becomes visible when installations model country variants such as German for Germany, Austria, and Switzerland as separate site languages, even when only a few pages differ by country rather than by language.

The team discussed that a more general model could distinguish language from country, brand, user role, behavior segment, logged-in user context, or consent-based targeting. André summarized the main keyword as moving from a single dimension to multiple dimensions. Eric noted that this would require rethinking backend interfaces so that variation layers are not purely language-centered.

The team did not treat the dimension model as the immediate solution for the Dialog Days. Instead, it serves as a perspective showing that language is one example of a broader content-context problem. The more immediate message remains the need to improve TYPO3's handling of regional structural deviations.

## Topic 6: Fallback Visibility Case from Slack

During the meeting, André noticed a discussion in the initiative's Slack channel. Thomas had described a site using fallback mode where some content elements should be hidden in a translation. A previous workaround had been to translate an element with an empty text or a different `CType`, but TYPO3 v13's stricter `CType` alignment for translations made that workaround less viable for certain content elements.

Eric and André analyzed the actual problem behind the `CType` workaround. In fallback mode, omitting a translation intentionally triggers fallback content. However, editors need a way to express that a specific translated content element should not be shown and should not fall back either. André expected that translating an element and disabling the translation should prevent fallback to the default-language element. Eric agreed that this would give the disabled state a clear meaning distinct from a missing translation.

André reproduced the behavior in a test setup during the meeting. Disabling a translated connected content element still caused the default-language fallback element to appear. The team therefore treated this as a real missing capability in Core fallback handling rather than a pure `CType` problem.

Benni referred in Slack to an older extension named Language Visibility, which apparently allowed visibility decisions per language for pages, content, news, and other elements. Eric interpreted this as confirmation that the underlying need is real, even if a Core solution would need to avoid adding more confusing controls.

The team discussed whether disabled translations blocking fallback would be a Core change or an extension-level edge case. André considered it a missing Core feature because fallback mode currently gives editors no simple way to suppress individual fallback content. Eric noted that such a change could be breaking if existing installations rely on fallback content appearing despite a disabled translation, but still saw the case as a strong example for the Dialog Days: TYPO3 needs clear product decisions for regional content behavior.

Eric connected the case to the initiative's long-term synchronization direction. In a future model, fallback behavior could be replaced or reduced by explicit synchronization into target languages. Editors would then have clearer control over whether a synchronized or translated element is shown, hidden, or intentionally absent.
