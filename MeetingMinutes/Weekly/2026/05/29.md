## Topic 2: Hidden Default Language and Shadow Records

Eric recapped the concept discussed in the previous meetings. The current Connected Mode forces editors either to switch an entire translation into Free Mode when adding content that does not exist in the default language, or to create an otherwise unnecessary default-language record first and then translate it. The initiative had therefore discussed a hidden structural default layer in which `sys_language_uid = 0` continues to provide the structure, while the visible backend only exposes real editorial languages.

In that model, adding a content element in a translation would automatically create a corresponding shadow record in the structural layer. The translation could remain connected through `l10n_parent`, but the editor would not have to maintain visible content in the current default-language column. Eric connected this to the idea of an editing language that defines the main working context in the backend. This editing language would not be the backend UI language, but the language used as the editorial basis for the Page Module and Page Tree.

Eric emphasized the strategic context. The initiative needs a clearer visual and conceptual story before approaching the TYPO3 Product Strategy Group and Core contributors. He noted that official strategy alignment is important because some Core developers are unlikely to engage deeply with translation handling topics unless the topic is visible in the TYPO3 product strategy.

## Topic 3: Extension-Based Prototype Versus Concept Work

André suggested that the hidden-structure idea could perhaps start as an extension. His first technical sketch was to set the page-level `l18n_cfg` option so the default translation of a page is hidden, configure the default site language as a non-output structural language, and then reshape the backend interface around that behavior. A later step could use `DataHandler` hooks or similar mechanisms to create the default-language partner record automatically when an editor creates a content element in a translation.

Eric understood the attraction of prototyping inside the real backend, because the team would see the idea directly in TYPO3. At the same time, he warned that implementation work could easily consume the effort that is still needed for the strategic concept. He mentioned Georg Ringer's earlier page tree translation extension as something worth inspecting, but kept the main concern on whether the initiative should build immediately or first describe the desired editor experience more clearly.

André argued for a hybrid approach. A prototype could reveal mistakes that are hard to find in abstract planning, while still avoiding a huge Core patch at the beginning. He compared this with other TYPO3 initiatives that first build adjacent extensions and then contribute parts back into Core. Eric agreed that the work is large either way because the concept changes more than a small interface detail.

## Topic 4: Creating Content in Translations While Staying Connected

The team translated the concept into concrete backend operations. Eric summarized the desired behavior as making the current workaround the status quo: default-language records exist structurally in the database, but the backend display hides the default language and lets editors work directly in translations. André suggested that the default-language column should remain visible during early development because it helps verify whether the automatic creation of shadow records works.

Eric focused on the "new content element" workflow in the Page Module. When a new `tt_content` record is created in a translation, the system should automatically create the connected default-language record in the background. Since TYPO3 v14 enforces `CType` consistency for connected translations, the type would already be aligned. The team left open whether a shadow record needs an explicit marker, whether text fields should be copied into it, or whether the structural record should stay empty.

The participants discussed which controls would have to move from the default-language column into the translation column. The translation column would need the same editorial affordances currently available in the default language, including a create button and drag-and-drop behavior. André asked whether those controls would appear only in the selected editing language. Eric clarified that the editing language would act as the source-like editorial basis, while the hidden structural layer remains in the background.

## Topic 5: Placeholder Visibility and Sorting Semantics

The discussion then moved to untranslated placeholders. Eric explored whether a target-language column should show placeholders for all shadow records from every language, or only for records that exist in the selected editing language. Showing all placeholders would preserve full structure, but could make the interface very crowded on installations where multiple languages have independent additions.

André pointed out that sorting is only reliable when all structurally relevant records are visible. If hidden records from other languages sit between two visible elements, moving one visible element can have different effects in another language depending on the exact target position in the structural order. Eric reproduced this with a small backend scenario and agreed that reliable moving requires awareness of all shadow records.

The team considered several UI approaches. One option would be to allow moving only in a mode that displays all untranslated shadow records, while hiding cut-and-paste and drag-and-drop move controls in reduced views. Another option would be to open a wizard or modal only when a move has ambiguous target positions. The modal would show the relevant shadow records graphically and ask the editor to choose the exact structural position. Martin considered this more controlled than expanding the page column suddenly during drag and drop, especially on large multilingual pages.

The same problem applies when editors create new translated content. The structural position of the automatically created shadow record determines where untranslated placeholders appear in other languages. Eric noted that forcing editors back into a separate structural view would resemble the current default-language workflow too closely, so the goal remains to create content directly in a translation while still making the structural consequences understandable.

## Topic 6: Permissions for Structural Changes

André raised the permission problem that follows from cross-language structural sorting. If a French editor is allowed to move an element in the selected editing language, the resulting `sorting` changes may affect records that belong to other languages. Eric concluded that structural modification needs an explicit permission model and that, in the default case, probably only one configured language should allow structural changes.

André explained that TYPO3 already writes the `sorting` field globally for all elements on a page. In his view, this makes language-specific sorting permissions difficult because the same field has to be updated for records across languages. Eric connected this to the current backend model, where structural changes are effectively tied to the default language, and the initiative's proposal would make that structural lead configurable rather than hard-coded.

## Topic 7: Backend Permission Test and Free Mode Behavior

Eric created a non-admin backend editor during the meeting to test current TYPO3 v14 behavior with language restrictions. The user was configured with Spanish as the only allowed language, required a backend user group for table and module permissions, and needed Live Workspace access because Workspaces was installed. André and Martin helped identify missing permission pieces while Eric adjusted the backend user and group.

In Language Comparison, the Spanish-only editor could see the default-language context but could not effectively drag and drop connected translated content. The interface still allowed the user to pick up an element visually, but TYPO3 did not accept the drop target. Eric considered this a small UI bug because the drag affordance should ideally not appear when the operation is impossible.

When the page was switched into Free Mode, the same editor could create and move Spanish content. Eric observed that this explains why the drag-and-drop affordance exists in translated columns, although it is not valid for connected content in the tested permission setup. He noted that the Free Mode column can become visually large and less suited to the current connected-layout grid.

The team then looked at an older mixed-mode scenario from a previously investigated Forge ticket, but no ticket number was stated in the meeting. Eric described a video in which an editor starts in Free Mode, translates a previously untranslated element, receives a `l10n_parent`, and thereby enters Mixed Mode. In the current TYPO3 v14 workflow, the first action on an empty translation forces an earlier choice between Translate and Copy, and the language selector opens a wizard that keeps the parent relation at `0`. Eric noted that the inconsistency can still be forced by explicitly setting the connection field, but the demonstrated old workflow is no longer directly reproducible in the same way.
