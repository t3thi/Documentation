## Topic 1: Git-Native Knowledge System and Current State

Eric presented the documentation work that had grown out of the preparation for TYPO3 DevDays. The Current State now describes the initiative's observed needs, present Core behavior, open questions, vision, and recommended work. A separate maintenance document defines how new evidence and patch-status changes can be incorporated without losing the narrative structure.

Eric had extended this approach with a Git-native knowledge system based on [Andrej Karpathy's LLM Wiki pattern](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f), which Ulrich Mathes had recommended. The intended workflow uses AI assistance to compare new sources such as reviewed Meeting Minutes with structured Knowledge Objects. Durable semantic changes are recorded explicitly, while deterministic build tools generate human-readable views such as the English and German Current State. Eric had already added the initial implementation under the Documentation repository's [KnowledgeSystem directory](https://github.com/t3thi/Documentation/tree/main/KnowledgeSystem). He emphasized that he was still evaluating whether the approach worked reliably, although the generated document already appeared useful.

As an example, Eric had clarified that removing the special semantics associated with `sys_language_uid = -1` and `sys_language_uid = 0` was considered a prerequisite for using `BCP 47` language tags as unambiguous language identities. He also explained the Current State's separation of Language Identity, Synchronization Intent, Structural Identity, and Output Policy. The document deliberately contains recommendations rather than a selected long-term architecture, because fundamental Core decisions require an appropriate Core or product-strategy authority.

The documented working model describes the initiative's activities as research, vision development, bounded incremental improvement, and critical alignment of proposed patches with the vision. Eric hoped that the emerging unit structure and a clearer Core Team contact would improve the path from initiative recommendations to authorized decisions and mergeable changes. André considered the existing summary accurate and useful but found the complete material extensive. Eric therefore considered adding a short, prominent executive summary comparable to the concise DevDays presentation.

## Topic 2: Core Patches and Page Type Synchronization

Eric reported that the two most recently merged Core patches were [Gerrit patch #95170, "[BUGFIX] Fix free mode rendering in comparison view"](https://review.typo3.org/c/Packages/TYPO3.CMS/+/95170) and [Gerrit patch #95178, "[TASK] Sticky language header in comparison view"](https://review.typo3.org/c/Packages/TYPO3.CMS/+/95178). Patch #95170 fixed the rendering of Free mode content in the comparison view, allowing Free and Connected mode content to be represented together without elements disappearing after the latest security release. Patch #95178 added a sticky language header to the comparison view. André welcomed that both patches had been integrated.

The team then discussed André's comparatively small [Gerrit patch #95038](https://review.typo3.org/c/Packages/TYPO3.CMS/+/95038) for synchronizing the page type. André described the central question as whether translated pages should be allowed to use a different functional type. Eric related the proposal to the existing synchronization of content-element types: translating a record should not by itself change the record's semantics or functionality. A standard page and a shortcut page, for example, represent substantially different behavior.

Eric described intentional structural variation as a separate concern. If one language needs a shortcut while another needs a standard page, the model should use separate language-specific pages and intentional absence rather than changing the page type inside one translation connection. Existing page configuration through `l18n_cfg` can already suppress the default-language page where required. On that basis, the participants found no immediate conceptual objection to synchronizing the page type. Eric suggested reviewing the patch in detail outside the meeting and obtaining support from a Core merger rather than performing a line-by-line review during the call.

## Topic 3: Language Identity, Special Values, and Locales

André recounted a discussion with Benni after DevDays. André no longer regarded eliminating `sys_language_uid = -1` as necessarily the first strategic goal if the language semantics of `sys_language_uid = 0` could be separated from its structural role. He considered retaining a hidden structural layer potentially less disruptive than immediately duplicating every record and introducing synchronization processes whose operational behavior was still unresolved. Small installations without additional queue infrastructure would also have to remain supported.

Benni had suggested introducing `BCP 47` identifiers alongside the existing numeric language IDs as an incremental first step. He had also proposed replacing direct occurrences of `0` and `-1` in Core code with central constants so that the affected behavior became easier to identify. Eric considered both directions useful. He explained that the previous priority given to removing `-1` had followed repeated guidance from Core discussions with Lolli, but he was open to reassessing the sequence.

Eric regarded an explicit `BCP 47` field as a valuable early migration anchor because administrators could assign the intended semantic tag to each existing numeric ID. André distinguished this language identity from the server locale used for date and number formatting. A valid language tag such as a European English variant does not necessarily have a corresponding installed server locale, so the two responsibilities cannot be merged reliably.

The team considered using the new language tag for semantic output such as `hreflang`, while retaining the current explicit `hreflang` override. If no explicit value exists, `hreflang` could fall back to the new `BCP 47` field and, during migration, to the existing locale. Eric preferred eventually requiring the new identifier because it would be the reliable basis for migrating numeric IDs. The team also wanted to audit every present Core use of the locale and decide case by case whether it required a semantic language identity or an operating-system locale. No final migration sequence was selected.

## Topic 4: Hidden Structural Layer Prototype

André proposed retaining `sys_language_uid = 0` internally as the structural database layer because Core and extensions contain many numeric comparisons against zero. The language currently associated with that layer would move to a concrete positive language ID, while the zero layer would become invisible in the backend and would no longer provide frontend content.

As a first prototype, creating content in the designated visible language would automatically create a corresponding structural shadow record in the hidden zero layer. Existing content stored in zero would have to be migrated to a concrete language. The hidden record would continue to provide sorting and database structure, allowing much of the current Core and extension behavior to remain intact while editors worked exclusively in real languages.

The discussion exposed additional questions around `l10n_diffsource` and translation sources. Eric asked whether content from a designated structural language should be copied into the hidden record so that current synchronization mechanisms could be reused. André noted that `l10n_diffsource` already loses useful information too easily when a record is saved and does not provide the history needed for asynchronous translation workflows. For an editor translating from English into Chinese while German is the current default, the relevant comparison source may be `l10n_source` rather than the default-language content. The team treated the diff and source model as a separate unresolved concern that the prototype would need to expose rather than silently preserve.

## Topic 5: Structural Permissions and Synchronization UX

Eric and André discussed whether one visible language should receive privileged structural authority. André preferred a model in which every language could potentially initiate a cross-language structural change. Eric distinguished installations where editors may change shared structure from installations where country or translation editors must only translate content within an existing structure.

The participants converged on backend permissions as a possible way to cover both cases. A user with structural editing permission could move elements, create language-specific elements, and make changes that affect other languages. A translation-only user would work within the supplied structure and could edit textual content but could not add or rearrange structural elements. This would avoid assigning permanent structural superiority to one language while still allowing installations to restrict structural authority.

The same discussion was applied to field synchronization. A field enforced by `l10n_mode = exclude` could be editable from every language if the interface clearly indicated that the change affected all languages. A field using `allowLanguageSynchronization` would either keep a custom value for the current record or remain synchronized with its source. Eric and André regarded the main distinction as whether synchronization was mandatory or editorially optional. They considered a unified and explicit user experience possible, but source selection and the exact authorization model remained to be designed and tested.

## Topic 6: Fallback Scope

André questioned whether fallback behavior needed to remain exclusively a site-language setting. He suggested that a page-level or record-level value could allow fallback for selected content while retaining strict behavior elsewhere. Eric agreed that per-page variation was a valid use case and recalled that earlier TypoScript configurations could vary the behavior by page.

The team considered an inheritable page property a possible future enhancement. André classified it as useful but not part of the immediate prototype. The discussion did not select a replacement for the current site-level strict and fallback configuration.

## Topic 7: Language-All Visibility and Shadow Record Lifecycle

For the existing `sys_language_uid = -1` behavior, André observed that the shared record could remain technically unchanged if the backend displayed it in every language. Eric proposed rendering each language-all record in every language column at the same sorting position where it appears in the frontend. This would reduce discrepancies between backend editing and frontend output and prepare editors for a later migration from one shared record to explicit language records without changing the visible editing model.

The team also examined the lifecycle of hidden structural records. If a language-specific record is deleted and no other translation uses its shadow, the corresponding zero-layer shadow should be removed. In a fully independent structure, every language-specific element could have its own shadow, comparable to Free mode. Reconnecting two previously independent elements would require choosing which shadow survives and defining whether an accidental reconnection can be undone without losing earlier settings. The participants wanted the prototype to make these edge cases visible before committing to an architecture.

Eric proposed keeping current `-1` behavior unchanged while preparing a small initial patch that displays language-all records in every language. He intended to investigate building that patch before the next meeting. The larger hidden-default prototype would then be used to test creation, sorting, deletion, reconnection, permissions, and usability. Eric also invited the participants to review other merge-ready patches referenced by the Current State when time permitted.
