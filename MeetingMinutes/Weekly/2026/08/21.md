## Topic 1: TYPO3 Upgrade Experiences and AI Assistance (Off-Topic)

André described an ongoing upgrade from TYPO3 v11 to v14. He was evaluating which existing custom TCA content elements should be migrated to Content Blocks. Eric recommended using Content Blocks when custom elements already required substantial adaptation, because their YAML-based structure would reduce future coupling to Core TCA changes and keep the implementation focused on the content elements' business logic.

Martin shared a separate experiment in which he had allowed Claude, Rector, and Fractor to perform an upgrade of a small TYPO3 v10 installation to v14 with two custom extensions and otherwise mostly Core components. The result had worked surprisingly well with little manual direction. Eric considered specialized TYPO3 upgrade skills and deliberate review especially important for larger installations, while Martin regarded the experiment as evidence that current AI tooling could already handle suitably bounded projects effectively.

## Topic 2: Language-All Visualization Prototype and Sorting Behavior

Eric demonstrated a functional prototype that renders one `sys_language_uid = -1` content record in every language column of the Layout module's comparison view. Every occurrence represents the same database record, so editing it updates all columns. The prototype had not yet been submitted to Gerrit because Eric wanted to review the generated implementation carefully and prepare a proper Forge issue first.

Moving the Language-All record worked predictably in Connected Mode, where the comparison rows follow the Default Language structure. The team noted that the exact sorting contract still required technical verification. Free Mode exposed the existing limitation more clearly: one shared record has only one sorting value, while independently structured language columns may use unrelated sorting ranges. The record is already rendered in every frontend language today, but its position among Free-Mode records can therefore appear arbitrary. The prototype makes this existing discrepancy visible in the backend and lets editors reposition surrounding Free-Mode records relative to it.

The demonstration also uncovered a concrete move regression. Moving a normal language-specific record after a Language-All record caused the moved record to adopt `sys_language_uid = -1`, because the move operation derived the target language from the preceding record. Eric and Martin agreed that moving after a Language-All record must retain the moved record's original language and that this safeguard should be included in the bounded visualization patch when it can be implemented narrowly.

## Topic 3: Language-All Permissions and Migration Boundaries

The participants examined whether displaying Language-All records in every comparison column would grant additional editing rights to language-restricted editors. A test user restricted to French could edit the Language-All record from the French column but could not edit ordinary Default-Language content. The prototype itself only changes Layout-module rendering and related JavaScript; it does not alter record-level permissions. The observed access therefore appeared to follow the existing record permissions rather than a new authorization rule introduced by the patch, although Eric planned to verify the implementation in detail.

The Free-Mode discussion also clarified migration limits. If the future model reconnects currently independent structures through shadow records, existing Free-Mode elements cannot be matched automatically with certainty. A migration wizard may propose connections from available provenance such as `l10n_source`, but editors must make the final decision because the database does not prove that two independently created records belong together.

For the initial replacement of Language-All semantics, the team treated sorting as part of complete-record synchronization rather than as an independently configurable value. Placing synchronized content at a different position in one language while retaining shared content was considered a much later use case that could require duplication or selected-language synchronization. No such granular synchronization model was selected.

## Topic 4: TYPO3 v14.3.6 Child-Language Regressions

The team reviewed two new reports from Johannes Rebhan. [Forge issue #110497](https://forge.typo3.org/issues/110497) describes translated IRRE children receiving an incorrect `sys_language_uid` when their language field is disabled in TCEFORM. [Forge issue #110498](https://forge.typo3.org/issues/110498) reports a related case in which a `sys_file_reference` created for a free, non-default-language Extbase record receives language `0` instead of the language of its parent. Both issues were new and assigned to Tymoteusz Motylewski at the time of the meeting.

The participants considered the reports potentially related because both concern hidden child-language fields and newly created relations. They reaffirmed that a language-aware child should normally use the same concrete language as its parent; the explicit Language-All case remains the only discussed exception. A non-default-language parent combined with a child in language `0` or another unrelated concrete language was regarded as inconsistent.

An AI-assisted search identified the merged TYPO3 v14.3 commits ["Enhance workspace handling of language synchronization"](https://github.com/TYPO3/typo3/commit/ba453da8993) and ["Find translations with empty l10n_source"](https://github.com/TYPO3/typo3/commit/faf60eea222) as candidates worth inspecting. The team explicitly did not establish either change as the cause. In particular, the workspace-focused change would not explain a reproduction in live Workspace ID `0` without additional evidence. Eric intended to reproduce the failures, inspect the relevant TYPO3 v14.3.5-to-v14.3.6 changes, and report the preliminary assessment to Johannes.
