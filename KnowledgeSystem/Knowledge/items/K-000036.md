# Source-language choice and deleted-source recovery need an editorial contract

## Statement

Should a target-language workflow keep using the same content source or allow
per-record alternatives, and when should a vanished source reset that choice?
The prototype makes this visible through missing-translation placeholders and
proposed per-record Translate actions. Source choice must remain distinct
from structural parentage and the editor's current viewing context.

## Rationale

The meeting contrasted source drift with a valid German-to-US-English setup
that later needs British English as source. Eric preferred preserving existing
restrictions in the initial scope; André argued that contextual translation
actions expose the need for flexibility. Permission or TSconfig controls were
options, not a selected contract.

Static inspection qualifies the meeting's first-source shorthand. The current
page-wizard filter derives a set of source languages from existing target
content's positive source references and non-deleted source rows. It retains
all available sources when no target page translation or no used-source set
exists. This is not an immutable first-selection setting and can include more
than one source language. It does not prove that the observed deleted-source
case is harmless or establish a runtime regression; other paths and the
deletion lifecycle were not fully tested.

## Consequences

Characterize source removal, restoration, surviving references, multiple source
languages and wizard entry points before choosing automatic cleanup or a more
flexible policy. No missing-source Core issue number or fix is asserted here.
This question does not reopen the existing structural-parent requirements or
authorize broad site-language deletion cleanup.
