# Synthetic Language-All sentinels should be removed from backend selection

## Statement

The initiative's current direction is to eliminate synthetic `-1` values from
backend display, comparison and filter selection wherever the intended state
can be expressed as an explicit set of concrete languages. TYPO3 v15 already
offers a multi-select for comparison-language overlays, so selecting every
available overlay does not inherently require a fictitious additional
language. During migration, `-1` should remain associated only with an editor
deliberately choosing Language All in a record's language field. That stored
value represents record-wide synchronization intent rather than a human
language identity.

## Rationale

The same integer currently covers two different contracts: a value persisted
on a record and a synthetic backend option. A shared marker can make the code
more readable and searchable without resolving that semantic collision. For
the bounded marker patch, using one constant wherever `-1` means All Languages
is compatible with keeping the contracts conceptually distinct. Expressing UI
and filter selection as concrete IDs remains the longer-term direction where
the selected scope permits it, while reserving the persisted value for the
record-level intent preserves the meaning that must later be migrated to an
explicit synchronization model.

## Consequences

No occurrence may be removed solely because it contains `-1`. Each call path
must first be classified as a synthetic selection, an actual lookup of
Language-All records, or a fallback with a third meaning. Current Core still
uses a synthetic `SiteLanguage(-1)` in Layout, translates `-1` to the
Workspaces filter value `all`, and includes persisted Language-All records in
routing and sitemap queries. The review on 2026-09-18 additionally confirmed
that `ContentObjectRenderer`, the frontend `CategoryCollection` and Extbase's
`Typo3DbQueryParser` deliberately select records stored with Language All.
Those are valid record-level marker uses. `LinkAnalyzer`, by contrast, uses
the record's actual language where available and also falls back to `-1` when
no usable record language exists. That fallback needs a distinct explicit
contract or representation before it can be changed. The implementation
sequence therefore requires characterization tests and explicit replacement
states before synthetic handling can be retired. This recommendation does not
yet change Core behavior, deprecate `sys_language_uid = -1`, or select the
final persisted synchronization contract.

For Gerrit 95619 specifically, the initiative agreed on 2026-09-25 not to
encode the persisted, synthetic and fallback meanings in separate constants
yet. Every occurrence still requires a plausibility check that `-1` actually
means All Languages, and the marker description must not imply that the
constant is limited to database language fields. This interim naming decision
does not make the underlying contracts equivalent, prevent a later split or
weaken the long-term replacement direction above.

The review on 2026-10-02 made that scope concrete: genuine All-Languages
values in TCA helpers and `SlugHelper` belong in the marker patch rather
than being excluded merely because they occur in configuration. The existing
`LinkAnalyzer` fallback and `EditableRestriction` are accepted for naming
without changing their behavior or query representation. This is not a claim
that fallback metadata and an editor's stored synchronization intent are the
same contract. Layout drag-and-drop TypeScript retains its literal with a
PHP-marker synchronization comment for now; a shared JavaScript constant or
an explicit `isAllLanguage` property is a separate follow-up. A general
annotation rule for inverse range checks and context-only code remains open.

The post-meeting mainline check qualifies the meeting's low-risk assessment
of missing record language: the bulk query explicitly includes the language
field, whereas `recheckLinks()` does not explicitly add it to its selection.
It passes the selected row through `analyzeRecord()` to `checkLinks()`, where
an absent language field triggers `-1`. A field may still arrive incidentally
through other selected fields or event enrichment. The code therefore leaves
a concrete coverage question for characterization, not proof of an observed
runtime regression. Naming the fallback does not resolve that question.
