# Explore chain-driven output with explicit visibility synchronization

## Statement

André's proposal selects concrete requested-language content without consulting
the Default Language parent's visibility when no fallback chain is configured.
Single-language and all-related-language enable/disable operations would write
the existing `hidden` values explicitly. Equivalent API support, potentially
in `DataHandler`, would be needed; a separate stored Disable-All flag was not
selected. This seeks to preserve relevant Strict visibility behavior at write
time rather than through repeated frontend parent checks.

A configured site fallback chain would still be evaluated at runtime. Its
presence or absence could replace the separate `fallbackType` selector. In
this model, a missing connected translation permits configured fallback, but
an existing deliberately disabled translation blocks it locally. Deleting
that translation would permit fallback again. Structural connection alone
would not activate fallback without a configured chain.

## Rationale

Explicit visibility writes could simplify requested-language queries. Copying
complete fallback records, inline children and references is a much larger
synchronization problem, so the proposal retains runtime fallback rather than
materializing all fallback results. Output, structural connection and
editorial synchronization remain separate responsibilities.

## Consequences

This is a participant proposal, not current Core behavior or an initiative
decision. Eric and Martin did not yet regard its implications as fully
understood; further explanation and validation were deferred. No v15 release
commitment was made, and equivalence to all existing Strict behavior is not
proven.

The accepted requirement `K-000013` remains intact. Migration must preserve
existing output intent: an inactive saved chain under `strict` or `free` must
not silently become active merely because a selector disappears. The earlier
regional-use refinement in `K-000024` and rejection of destructive chain
cleanup in `K-000025` remain applicable; the new proposal does not reverse
them. Hidden-versus-missing semantics, configuration scope, existing data,
permissions, Workspaces and consistent Core/Extbase/custom-query behavior
still require product, compatibility and code-path validation.
